## 2 数据清洗规则是什么

### 2.1 缺失、异常和类型处理

| 数据 | 清洗规则 |
| --- | --- |
| 正文 comment 缺失或仅有空白 | 填为空字符串，并设置 comment_missing=1；其他记录为 0 |
| 标题 title 为空值 | 填为空字符串；非空原文保留 |
| 点赞数 votes 非法或为负数 | 替换为 0，并设置 votes_invalid=1；正常记录为 0 |
| votes、time、rating | 转换为整数类型；time 仍是毫秒时间戳，rating 的评分数值不改 |
| purchased | True 转为 1，False 转为 0 |
| 各类 ID | 保留为字符串 |

点赞数异常时填 0 是处理约定，不代表已确认真实点赞数为 0。标题、正文不会因与评分情感不一致而被修改。

### 2.2 重复和评分冲突处理

用原始数据的以下 8 个字段判断输入是否完全相同：

**title、comment、user_id、prod_id、parent_prod_id、time、votes、purchased。**

- 上述字段相同，rating 也相同：只保留一条。保留哪个 ID 采用固定规则，不随机挑选。
- 上述字段相同，但 rating 不同：相关记录全部删除。例如评分为 5、5、1 的三条记录，全部删除。
- 仅标题、正文相同，但用户、产品、时间等其他字段不同：不因此删除。
- 不采用平均评分，不主观选择“正确评分”。

| 处理结果 | 记录数 |
| --- | ---: |
| 原始训练数据 | 7,684,645 |
| 删除评分冲突记录 | 28,518 |
| 删除评分一致的多余重复记录 | 25,157 |
| 合计删除 | 53,675 |
| 最终保留 | **7,630,970** |

原始 CSV 保留。评分冲突的产生原因未确认，不直接认定为系统或录入错误。

## 3 清洗完的数据长什么样

**每一行仍是一条保留的评论。**清洗后的完整训练数据保存在 output/clean_train_latest，使用 Parquet 格式，包含以下 12 列：

| 字段 | 内容／类型 |
| --- | --- |
| id | 评论 ID，字符串 |
| title | 标题，字符串 |
| comment | 正文，字符串；缺失时为空字符串 |
| user_id | 用户 ID，字符串 |
| prod_id | 产品 ID，字符串 |
| parent_prod_id | 父产品 ID，字符串 |
| time | 原始毫秒时间戳，长整数 |
| votes | 清洗后的点赞数，长整数 |
| purchased | 是否购买，整数 0／1 |
| rating | 原始评分，整数 1～5，作为预测目标 |
| comment_missing | 正文缺失标记，整数 0／1 |
| votes_invalid | 点赞数异常标记，整数 0／1 |

这份数据共有 **7,630,970 行、12 列**。其中正文缺失标记为 1 的有 8,955 条，点赞数异常标记为 1 的有 1 条。已完成的字段有效性检查未发现剩余非法记录。

它是清洗阶段的数据，还没有文本数值向量；B 训练时主要读取第 6 节中的最终特征文件。

## 4 全部做了哪些特征处理

### 4.1 基础数值特征 11 个

| 特征名 | 含义 |
| --- | --- |
| title_char_count | 标题字符数 |
| comment_char_count | 正文字符数 |
| title_word_count | 标题分词后的词数 |
| comment_word_count | 正文分词后的词数 |
| votes | 清洗后的点赞数 |
| votes_log | ln(1 + 点赞数)，压缩极大数值 |
| purchased | 是否购买，0／1 |
| review_year | 评论发布年份，按 UTC 提取 |
| review_month | 评论发布月份，按 UTC 提取 |
| comment_missing | 正文缺失标记 |
| votes_invalid | 点赞数异常替换标记 |

字符数按清洗后保留的文本计算；词数按下面的分词规则计算。

### 4.2 文本特征 2 列

标题和正文分别执行：移除分词用文本中的 HTML 标签、整理空白、统一小写、分词，然后转换为数值向量。原始文本保留在前面的清洗／基础特征数据中。

分词提取字母、数字组成的词，保留 don't 等词内撇号；不删除停用词，不提取表情特征。

| 特征列 | 内容 | 维度 |
| --- | --- | ---: |
| title_tfidf | 标题文本向量 | 65,536 |
| comment_tfidf | 正文文本向量 | 262,144 |

处理方式为 **HashingTF → IDF → L2 归一化**：计算词频、调整常见／少见词的权重，再统一每条文本向量的长度。使用稀疏存储，只保存有值的位置，不为每条评论保存完整的几十万个数值。

HashingTF 使用固定位置映射，不建立显式词表，不同词可能落在同一位置。IDF 的 minDocFreq 为 2。**IDF 只在 80% 训练部分拟合，验证部分使用同一套处理器转换。**

### 4.3 用户／产品统计字段 9 个

| 对象 | 评论数量 | 数量对数 | 未见标记 |
| --- | --- | --- | --- |
| 用户 | user_review_count | user_review_count_log | user_unseen |
| 产品 | product_review_count | product_review_count_log | product_unseen |
| 父产品 | parent_product_review_count | parent_product_review_count_log | parent_product_unseen |

- 数量仅从 **80% 训练部分**计算，训练记录的数量包含自身。
- 数量对数为 ln(1 + 数量)。
- 验证部分出现训练中没有的用户／产品时，数量填 0，对数为 0，未见标记为 1；正常匹配时标记为 0。
- 没有使用评分计算这些统计，也没有生成用户／产品平均评分。

验证记录中，47.81% 对应训练中未见的用户，3.27% 对应未见产品，2.63% 对应未见父产品。这些是记录比例，不能相加。三个未见标记在训练部分全部为 0，主要用于分析新用户／产品情况，不保证其自身能帮助模型预测。

### 4.4 最终特征数据结构

B 收到的最终特征数据，每行包含：

**id + rating + 11 个基础数值特征 + 9 个用户／产品统计字段 + 2 个文本向量列，共 24 列。**

原始评论文本和用户／产品 ID 不在最终特征文件中；如需进一步分析，可以按评论 id 从同一划分的数据中关联，不能按行号拼接。

**id 只用于对齐，rating 是预测目标，两者都不能作为输入特征。**文本向量已归一化，数值特征尚未标准化；B 应根据模型需要选择字段，并仅使用训练部分拟合任何缩放参数。

## 5 样本按照什么划分

从清洗后的 7,630,970 条记录中，**按 rating 分层进行可重复的随机化划分，固定参数 42**。每个评分分别取约 80% 训练、20% 验证，不取文件中连续的前 80%。

| 评分 | 训练部分 | 验证部分 |
| --- | ---: | ---: |
| 1 | 897,463 | 224,366 |
| 2 | 527,580 | 131,896 |
| 3 | 591,023 | 147,756 |
| 4 | 707,494 | 176,874 |
| 5 | 3,381,214 | 845,304 |
| 合计 | **6,104,774** | **1,526,196** |

每个评分取整后，比例非常接近 80%／20%。两部分没有相同评论 ID，评分分布接近。A、B 必须共用这一划分，不各自重新划分。

测试集未参与划分、IDF 拟合和用户／产品数量统计。评分冲突记录在划分前已被删除，因此验证 RMSE 代表过滤后数据的效果，报告中应披露这一点，不能假定原始测试数据也没有评分冲突。
